## 1. 问题与「要不要训模型」的决策过程

**问题**：用户导入任意格式的 txt，要自动切分章节、提取目录，并在阅读页生成可点击的目录。难点在 txt 没有任何格式契约——有人用「第一章」，有人用「01」，有人用「CHAPTER I」，有人纯散文没有章节。

用户一开始就问了那个核心问题：**「是不是需要训练一个小模型来做？」** 下面是当时反复权衡的完整链条，因为最终结论（先上规则、后上模型、两者共存）不是一步到位的，是被几轮质疑和真实数据逼出来的。

### 1.1 第一反应：反对训模型

理由有四条，当时都成立：

1. **业界惯例**：calibre 的 structure detection、开源阅读 Legado、各种小说站，处理这问题都是「规则 + 统计」，不是模型。章节标题的**表面模式极强**（第X章、Chapter N），正则一行就能判。
2. **部署成本**：mDeBERTa-v3-base int8 后约 280MB。weread 是纯前端 PWA，没有后端。让用户为导入一本 txt 先下几百 MB 模型不现实。
3. **可调试性**：正则错了改一行就行，能精确定位；模型错了是个黑盒，没法「改一行」。
4. **训练数据死结**：要微调得有标注好章节边界的语料。现实做法是拿 epub（自带目录）转 txt 自动生成标签——**但能被这样自动标注的样本，恰恰都是规则本就能匹配的样本**。模型学到的是规则的软化版，泛化不到规则覆盖不了的怪格式，因为怪格式你没有标签。这是最本质的反对理由，我称之为「同义反复陷阱」。

### 1.2 用户追问 mDeBERTa-v3-base，坚持要评估

我的回应是「用错了工具」：mDeBERTa 能解决的（判断单行像不像标题）恰恰是最简单的部分，正则就能做；它解决不了的（全书级的编号序列、目录页 vs 正文）它也做不了，因为逐行分类器看不到全局结构。加上前面的部署和数据问题，当时判断不划算。

### 1.3 两个信息改变了结论

- **「PWA 离线能接受体积」**：用户指出这是离线阅读器，模型下一次永久缓存，280MB 可接受。部署成本这条被消解了一半。
- **「多语言呢？支持更多语言不是更好」**：这是**真正扭转判断的点**。规则库的多语言维护成本是**线性**的——中文「第X章」、英文 Chapter、法语 Chapitre、德语 Kapitel、日语「第X話」、俄语 Глава……每种语言都要人工攒模式库，长尾语言没人帮你踩坑。而多语言模型学到的「标题性」特征是**跨语言共享**的，还能靠零样本迁移覆盖没有训练数据的语言。280MB 全量词表换 ~100 种语言的入场券，对一个多语言阅读器是划算的买卖。

**于是结论定型**：值得上模型，但**架构上模型只替换候选生成层，不替换整条流水线**（这个判断从头到尾没变，也被后来的实践反复证明是对的，见第 4、7 节）。

> **经验 0（元经验）**：「要不要上模型」不是一个静态的技术判断，而是随**约束条件**（部署形态、目标语言数、能否拿到独立标签源）变化的。最初反对的三条理由，两条被新约束消解（PWA 可离线、多语言值得），一条被新数据源解开（epub 目录，见第 4 节）。别把早期结论当定论——当输入变了，重新算账。

> **经验 1（架构直觉要用真实数据验证）**：我当时论证「正则能覆盖 95%」是**在没有真实语料的情况下拍的**。后来一跑真实语料，实际只有 54%（见第 3 节）。空气里论证覆盖率毫无意义，尽早拿真实数据打脸自己。

## 2. 三层规则流水线（P1，至今仍是基座）

`lib/chapter/` 落地了三层，这是无论上不上模型都要写的：

1. **候选生成** `patterns.ts` + `candidates.ts`：多语言模式库（第X章 / Chapter N / 一、/ 1. / 罗马数字 / 序章后记 / 【】），逐行匹配，行长过滤（≤50 字）。关键防误报：编号词后必须接分隔符或行尾，否则「他翻到第三章」这种正文短句会被误判。
2. **全局验证** `validate.ts`：
   - 家族竞争打分（同一本书里 cn-chapter、num-enum 等模式家族抢主导权，按数量 × 编号连贯度 × 家族精度权重）；
   - 最长递增子序列剔除离群（正文里偶然出现的「第五章」引用不构成序列，被踢掉）；
   - 最小间距过滤（两个「章节」只隔 50 字必是误报）；
   - 覆盖度检查（章节只挤在开头 = 目录页，不是正文章节）。
   - **这层是精度的真正来源，且完全语言无关。**
3. **兜底**：无命中则整本一章（保留原有行为）。

关键设计：`detectChaptersDetailed` 除了章节列表，还输出**置信度**（high/medium/low/none）+ 胜出模式家族——供后续决定「这本书要不要调模型增强」。

> **经验 2**：模型替换的是**候选生成**，不是整条流水线。全局结构问题（编号跨卷拼接、目录页 vs 正文、覆盖度）模型解决不了，必须留给确定性代码。逐行分类器只回答「这一行像不像标题」，它没有全书视角。这条判断贯穿始终，是整个方案没有走偏的定海神针。

## 3. 真实语料撕碎了「95% 覆盖」的假设

拿到 `literature-books-master`（273 txt + 85 epub）后，写了 `evalRules.ts` 在其上跑规则层：

- high 置信度只有 **147/273（54%）**，完全未识别 **96/273（35%）**——远低于我拍的「~95%」。
- 又写 `diagnose.ts` 做失败归因：**52 本零候选**（无任何已知标记）、22 本候选不足、10 本被「30% 前缀检查」误杀。
- 具体撕碎点：
  - **金庸小说全军覆没**：回目是「一 青衫磊落险峰行」——中文数字 + **空格** + 语义标题，无「章」字。我的 cn-enum 要求分隔符是「、」「.」，空格不认。
  - **《四世同堂》用裸数字 `01`/`02`** 独占一行，无标题、无分隔符。
  - **《狼图腾》用「正文 1」**、《曾国藩全集》是**多卷本每卷重新从第一章编号**（1-9, 1-7, 1-6），LIS 只取到第一卷就被覆盖度检查误杀。

**然后我尝试补正则，实测了一次改动的代价**：

- 修好 28 本、**碰坏 13 本**（本来好好的《陆小凤传奇全集》被挤成 0 章）、**23 本误报爆炸**（「世界营销绝招800例」被切成 522 章）。
- 更狠的是：连我以为「结构性正确、精度安全」的多卷本修复，重跑后 high 仍从 147 掉到 130——因为「允许编号回落重启」等于放宽了序列校验，把更多噪声当成合法序列。

> **经验 3（最重要）**：纯正则识别自由格式文本会**打地鼠**——每放宽一条规则接住新格式，就在别处放进一批假阳性。这是**方法本身的上限**，不是努力能绕过的。而且「看起来有原则」的改动也逃不过精度-召回的跷跷板。判断一个方案会不会打地鼠，唯一可靠的办法是拿真实语料量化 delta（修好几本 / 碰坏几本 / 爆炸几本），而不是看单个 case 是否修好。

## 4. 路线反转：epub 目录解开了「数据死结」

第 1.1 节的第 4 条反对理由（同义反复陷阱）是最本质的。它被一个发现直接解开：

**85 个 epub 自带结构化目录（toc.ncx / nav.xhtml），是独立于规则正则的 ground truth。**

epub 的目录是出版商/制作者手工确定的真实章节结构，和「我的正则匹配什么」毫无关系。用它当标签，模型学的是「真实章节长什么样」，不是「规则匹配什么」。同义反复陷阱在**有独立标签源**时不成立。

于是决策定型：**规则层冻结在高精度（P1 版本）当模型的自动标注器 + 兜底，模型在候选层学规则学不会的语义标题**。

架构（从头到尾没变）：

```
候选层：模型逐行「是否标题」分类   ← 学正则学不会的语义标题（青衫磊落险峰行）
   +   规则模式库（高精度冻结）     ← 引导标注 + 模型未加载时兜底
结构层：多卷拼接 / 目录页剔除 / 覆盖度   ← 永远是 validate.ts，模型不碰
```

> **经验 4**：「训练数据死结」这类反对理由，要具体到「标签从哪来」。当出现一个**独立于待训模型的标签源**（这里是 epub 目录），死结就解开了。遇到「没法训，因为没标签」时，先穷尽找找有没有天然的、旁路的真值来源。

## 5. 训练踩的坑（每一个都值得记住）

数据管线 `ml/data/build_dataset.py`：epub 正文按 spine 顺序拍平成行，命中 toc.ncx 标题的行标正，其余标负。84/85 解析成功，23.6 万行、7983 正样本、正负比 1:29。

### 坑 5.1：类别不平衡直接崩

首次冷烟训练 f1=0。诊断：正负比 1:29，模型学成「全判非标题」——准确率 96% 但**零召回**，loss 还很低（0.067），完全在骗自己。

**解法**：负样本降采样（`train.py --neg-ratio`，默认 1:5），**只对训练集做，验证集保持自然分布**。放数据生成阶段会把验证集也采样导致精度虚高，所以放在 train.py 切分之后、只动训练集。平衡后冷烟 f1=0.37。

> **经验 5**：极端不平衡下，**看 f1/召回而非 loss**（全判负也有低 loss）。降采样只动训练集，评估集必须保自然分布，否则指标骗自己。

### 坑 5.2：DeBERTa-v3 微调发散成「死模型」

完整训练（batch 32、3 轮）又 f1=0。这次不是不平衡——诊断方法是**加载模型，手动对几个已知样本预测**，发现它对任何输入都输出**几乎相同的 logits**：「第一章 风雪夜」和「这个道理其实很简单」的标题概率都是 0.42，logits 几乎不随输入变化。这是「死模型 / 发散」，不是「偏向多数类」（后者会给多数类高概率）。DeBERTa-v3 微调以不稳定著称。

**定位方法**：冷烟（batch 16）能学、完整（batch 32）不能——**只改数据量这一个变量**，回到冷烟已证配置（batch 16 / lr 2e-5 / 2 轮）跑完整数据。修复后 f1 正常。事后加了 `--lr` 参数，注释写明「发散时降到 1e-5」。

> **经验 6**：模型「死掉」时别猜，**直接加载它对已知样本预测**——常数输出 = 没学到 / 发散，明显区别于「偏向多数类」。调超参**一次只改一个变量**，从已知能 work 的配置出发。DeBERTa-v3 对 batch/lr 敏感，发散优先减小 batch、降 lr。

### 坑 5.3：eval-limit 加速带来的指标虚高（自己骗自己）

为加速迭代（完整验证集 39k 行推理要 17 分钟/轮），训练时加了 `--eval-limit`，只在验证子集（保留全部正样本 + 抽 5000 负样本）上评估，报出 **precision 0.88 / f1 0.59**。

**但这是假的**——子集把负样本池缩小近 8 倍，假阳性少算，精度被抬高。算笔账：真实 566 个假阳性，在 1:4.8 的子集里只剩 ~74 个，精度就从 0.45 虚高到 0.88。在**完整验证集**上 v1 真实是 **precision 0.45 / recall 0.44**。

> **经验 7（血泪）**：任何为加速而对**评估集**做的采样都会污染指标本身。加速开关只能用于「训练中粗略监控趋势」，**最终结论必须在完整、自然分布的评估集上得出**。这个错误让我一度对外报了虚高数字，后来必须主动纠正。注意：召回不受负样本采样影响（分母是全部正样本），精度受影响——搞清楚每个指标的分母对采样敏不敏感。

### 坑 5.4：目录第一项 off-by-one（既有 bug，被新功能照出来）

接入阅读页后发现点目录第一项会跳过开头。根因在 `transformText.ts`：`titleIdPage` 用 `if (!titleIdPage[id])` 记录每章首页，而首章首页页码是 `0`，被 falsy 判断当成「未赋值」覆盖成第 2 页。改成与 `undefined` 比较。这是既有代码的潜伏 bug，因为规则以前识别不出章节、目录一直是空的，所以从没暴露。

补了回归测试，并**验证过测试真能抓 bug**：回退修复后测试失败（`expected 1 to be +0`）。第一版测试因为序言太短（只占 1 页）没复现，加长序言到跨多页才有效。

> **经验 8**：写回归测试后，**回退修复确认它真的会失败**——否则可能写了个永远通过的假测试。构造复现数据时要满足 bug 的触发条件（这里是「首章必须跨多页」）。

## 6. 召回瓶颈与格式特征（关键突破）

`threshold_sweep.py` 在完整验证集上扫阈值，结果很冷静：v1 光调阈值，召回从 0.44 **只能到 0.6**，且精度崩到 0.09。曲线很平——因为模型的漏判是**自信的漏判**：语义标题「累到无力抵抗」给的概率是 0.007，不是「差一点到 0.5」，降阈值根本捞不回。

**根因不在数据量，在特征**：模型只看到「文本行 + 前后行文本」，看不到人判断标题的真正依据——**这行是否短、是否以句号结尾、在全书什么位置、前后行相对长度**。拍平文本时这些信号全丢了。「累到无力抵抗」单独一行拿出来，你我也未必看得出是标题；线索在于「它很短、不以句号结尾、独占一行、后面跟着长段落」。

**解法**：把格式特征**离散成 token 拼进输入**（不改模型结构，导出 ONNX 零障碍，前端只要拼出一样的字符串）：

```
第一章 风雪夜  →  "L1 P0 Q0 NX1 PV0 [SEP] 上一行 [SEP] 第一章 风雪夜 [SEP] 下一行"
累到无力抵抗  →  "L0 P0 Q1 NX1 PV0 [SEP]  [SEP] 累到无力抵抗 [SEP] 当我们的自控力像肌肉一样疲劳时…"
```

- **L0-3** 行长桶、**P0/1** 是否以句末标点结尾（标题几乎不以「。」结尾，最强负向信号）、**Q0-3** 位置四分位、**NX/PV** 前后行是否明显更长（短标题后接长正文段）。
- **单一来源** `ml/textfeat.py`，前端 `lib/nlp/features.ts` **逐字复刻**，**34 个测试断言两侧输出逐字相等**（参照值直接从 Python 生成）。

效果（完整验证集诚实值）：**召回 0.44 → 0.90**，精度 0.45 → 0.24。语义标题「累到无力抵抗」现在带上 `L0 P0 NX1`（极短、不以句号结尾、后接长段落），正是它缺的信号。

> **经验 9**：当模型**自信地漏判**某类样本，往往是**缺特征而非缺数据**。问自己「人判断这类样本靠什么线索」，把那些线索显式喂进去。加数据对「缺特征」型的错误帮助有限。

> **经验 10**：训练/推理特征必须**逐字一致**，否则线上崩且极难排查（模型在训练集上好好的，线上全错）。把特征逻辑收进**单一来源**，另一侧复刻，用「参照值断言」测试锁死。这是最容易静默出错、又最该测的地方。跨语言（Python `len` 按码点 / JS `String.length` 按 UTF-16 码元）也要对齐——用 `[...str].length`。

## 7. 「高召回低精度」是正确的档位

精度 0.24 孤立看很差（报 6693 行找 1808 个真标题，约 4900 假阳性），但对「模型接结构层」的架构是**理想档位**：

- 模型负责**别漏**（召回 0.90）——漏了结构层补不回，没有编号序列可插值。
- 假阳性交给 `validate.ts` 结构层清：散乱的假阳性不构成递增章节序列、不满足最小间距和覆盖度，会被过滤掉——**低精度正是结构层能修的**。

训练时用 neg-ratio 1:4 主动偏向召回，就是这个考量。

> **经验 11**：不要孤立地看单个模型指标。在「模型 + 确定性后处理」系统里，把召回和精度的**职责分给不同层**：模型冲召回（漏了补不回），后处理保精度（假阳性可过滤）。脱离系统评价 0.24 精度会得出「模型很差」的错误结论。

## 8. 评估的严谨性（用户的关键提醒）

用户追问：验证集和训练集是否同源、会不会过拟合。核查后：

- **按书划分**（`split_by_book` 取排序后后 15% 的整本书当验证集），同一本书不跨训练/验证——防**风格泄漏**（同一本书章节风格一致，按行随机分会让模型作弊）。0.90 是在没训练过的书上测的。
- **去重在划分前**（按 text+label 全局去重），防同一 (text,label) 跨边界。
- **瑕疵（主动坦白）**：只有训练集 + 验证集，**无独立测试集**；`load_best_model_at_end` 按验证集 f1 选 epoch，验证指标**轻微乐观**。
- **更强兜底**：literature 目录的**中文 txt 从没进过训练**（训练只用了该目录的 epub + 英文 txt），是完全独立的第三方测试集（`test_independent.py`，用规则给结构化中文书打可靠 gold 标签）。做这个测试前还要比对书名，防「同名书既是训练 epub 又是测试 txt」的泄漏。

> **经验 12**：按**样本的自然分组**（这里是书）划分，而非按行随机，否则泄漏。只有 train/dev 时要主动说明模型选择带来的乐观，并尽量补一个**既不训练也不参与选择**的独立测试集。诚实交代评估的局限，比报一个漂亮数字重要——这条是用户逼出来的，也是最该内化的。

## 9. 工程与环境经验（每条都踩过）

### 9.1 Python / torch 版本地雷

- **症状**：`pip install -r requirements.txt` 报 `Could not find transformers>=4.44`，只找到 2.x。
- **根因**：机器上 `pip` 指向 **Python 2.7**（deprecation warning 泄露），在 2.x 包索引里找。而 `python3` 是 **Homebrew 的 3.14.5**，太新，**torch 没有对应 wheel**。
- **解法**：`python3.11 -m venv ml/.venv`，用 3.11 装（torch 支持到 3.12）。命令一律走 `.venv/bin/python`，不用系统 `pip`。
- **经验**：多 Python 环境下，`pip` / `python` 到底指向谁必须先确认（`which -a`）。用最新 Python 前先查关键依赖有没有 wheel——torch/onnxruntime 这类带原生扩展的，滞后新版本 Python 半年到一年很常见。

### 9.2 MPS 多进程死锁（最坑，一度以为是崩溃）

- **症状**：启动训练后日志**长时间零输出，然后进程消失**。第一反应以为是段错误 / 崩溃。
- **误判过程**：反复重跑，越跑越多进程；`ps | grep train.py` 有时抓不到（shell 怪异），加深了「崩溃」的错觉。
- **真相**：我为了「重试」启动了**3 个训练进程**，它们**抢同一块 MPS（Apple GPU）互相死锁在 step 0**。`ps aux` 一看，三个 python 进程都在，其中一个 55% CPU 空转。
- **解法**：`pkill -9 -f train.py` 全杀，只留一个干净进程。
- **经验**：Mac 上 MPS 是独占性强的单 GPU，**同时只跑一个训练/推理进程**。「静默无输出后退出」这种症状，先 `ps aux | grep` 数一下是不是多进程竞争，别急着当崩溃排查。后续所有长任务启动前都先 `pgrep -f ... | wc -l` 确认没有残留。

### 9.3 训练在 Mac 上到底多慢

- mDeBERTa-v3-base，batch 16，MPS 上约 **1.8 秒/步**（batch 32 会发散，见 5.2）。
- 完整训练（1.5-2 万训练行、2 轮）约 **1.5 小时**；验证集 39k-100k 行推理 **每轮 3-17 分钟**（用 `--eval-limit` 压到 2 分钟，但注意 5.3 的虚高陷阱——只用于监控趋势）。
- 独立测试集 15 万行推理约 30-40 分钟。
- **经验**：没有 CUDA 时，MPS 能训 base 级模型但慢一个量级；迭代要靠「小数据冷烟验证链路 → 全量正式训练」两段式，别一上来就全量。

### 9.4 输出被工具链过滤 / 编码问题

- **rtk 代理过滤 vitest 输出**：`pnpm test` 的详细结果被压掉，只剩汇总。需要原始输出时用 `rtk proxy <cmd>` 落到文件再读。
- **训练日志有非 UTF-8 字节**：`tr '\r' '\n'` 报 `Illegal byte sequence`。解法 `LC_ALL=C tr -cd '[:print:]\n\r'` 先过滤再处理。
- **进度条用 `\r` 刷新**：`tail` 直接看是一坨，要 `tr '\r' '\n'` 拆开取最后一行。
- **经验**：长时间后台任务的进度/结果，别指望终端实时看——统一重定向到文件，用 `grep -a` / `LC_ALL=C` 抗二进制字节，用完成条件轮询（`until ! pgrep ...; do sleep N; done`）等结束，不要手动 `sleep` 拼接。

### 9.5 vitest 收集了编译产物

- **症状**：测试数从 12 跳到 24，凭空多一倍。
- **根因**：`vite build` 产生的 `dist/` 里有编译后的 `.test.js`，vitest 4 默认把它们也收进来跑。
- **解法**：`vitest.config.ts` 显式 `exclude: ['**/dist/**', ...]`；顺带配 alias（vite 的 root 相对路径 alias 在 node 下不生效，要真实文件系统路径）。
- **经验**：测试数异常翻倍先查是不是重复收集了构建产物 / 快照。

### 9.6 磁盘与产物管理

- Trainer **每轮存 checkpoint**（mDeBERTa-base 各 ~3GB），一个 2 轮训练留下 6-7GB 中间产物。训练后 `rm -rf out/model/checkpoint-*` 只留最终模型。
- ONNX 导出产物：`model.onnx`（fp32，~1GB，不部署）+ `model_quantized.onnx`（int8，**322MB，浏览器加载这个**）+ tokenizer.json（15.6MB）。
- 全部走 `ml/.gitignore`（`train/out/`、`export/out/`、`data/out/`、`.venv/`、`*.jsonl`），**模型和数据集绝不进 git**。
- **经验**：训练前就把产物目录加进 gitignore，别等 `git status` 里冒出 1GB 文件才补。定期清 checkpoint。

### 9.7 ONNX 导出与量化

- 用 `optimum[onnxruntime]` 导出 + int8 动态量化，optimum 2.1 上脚本直接可用。
- **量化不损伤判别力**：验证量化后 ONNX 预测与 PyTorch 一致（标题 0.92-0.98、正文 0.002），用**浏览器同款 onnxruntime** 加载 `model_quantized.onnx` 复核，而不是只信 PyTorch。
- **经验**：量化后必须用**部署时的运行时**（这里是 onnxruntime，不是 PyTorch）复核几个样本，int8 偶尔会显著掉点，早发现。
